# Phase E — Cost analytics

A Python pipeline that turns per-ISP traffic data into a management-language
cost report with optimization recommendations. Bridges the gap between
network engineering ("AS-paths and local-pref") and finance ("which ISP
is costing us how much, and what would we save by changing routing").

## What it does

1. **Collect** — `collect_flows.py` polls ce1's interface counters via SSH
   every 10 seconds and writes per-ISP byte deltas to `flows.csv`.
2. **Analyze** — `analyze_costs.py` reads the CSV, applies a per-GB
   pricing model, projects monthly costs, and identifies optimization
   opportunities (traffic that could move to a cheaper ISP).

## Pricing model

Realistic-shaped enterprise ISP rates:

| ISP             | Rate         | Notes                            |
|-----------------|--------------|----------------------------------|
| Premium Fiber   | $0.05/GB     | Reserved for latency-sensitive   |
| Standard Cable  | $0.01/GB     | Cheapest, ideal for bulk traffic |
| LTE Backup      | $0.50/GB     | Expensive overage rates (10x premium) |

Real numbers vary by contract, but the *shape* of the relationship
(premium ~5x cheaper than backup, standard ~5x cheaper than premium)
holds across most enterprise contracts.

## Architecture choices

**Interface counters, not NetFlow.** Real production tools use NetFlow,
sFlow, or IPFIX which give per-flow detail (5-tuple, packet counts).
Interface counters give 80% of cost-analysis value with 10% of setup
complexity. NetFlow integration would be the natural Phase E.2 if we
extended this.

**Polling, not streaming.** Counter-deltas-by-polling is the simplest
viable approach. A streaming telemetry version (gNMI from cEOS into a
TSDB) would scale better but adds infrastructure. For a portfolio
deliverable, the simpler version demonstrates the same logic.

**Hardcoded ISP→interface mapping.** `INTERFACE_TO_ISP` in `collect_flows.py`
maps `Et1`/`Et2`/`Et3` on ce1 to the three ISPs. In a larger lab this
would come from configuration, not code.

## Lessons learned

1. **cEOS interface output uses short names (`Et1`)** in `show interfaces
   counters` rather than the full `Ethernet1`. Parsers must match the
   actual output format, not the configured interface names.

2. **Arista's `show interfaces counters` has two separate tables** —
   InOctets and OutOctets are not on the same row. Parser must split
   the output and merge.

3. **Counter deltas, not raw values.** Raw counters grow forever; cost
   analysis cares about traffic *during the observation window*. Delta
   computation between samples gives the right metric.

4. **Projection scaling.** Observed cost over a short window is meaningless
   to management. Projecting to monthly (`30 * 24 * 3600 / observation_seconds`)
   makes the numbers actionable.

## Limitations

- Assumes uniform traffic distribution across the observation window
  when projecting monthly costs (real traffic has peaks/valleys)
- Optimization analysis assumes a flat 50% of traffic is movable; real
  classification would require DSCP/port/protocol analysis
- Pricing model is per-GB only; real contracts often include commits,
  bursts, and tiered rates that this doesn't model
